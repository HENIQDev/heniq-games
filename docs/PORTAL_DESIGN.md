### 1-3 結論：HP の中でやるのは難しい
HP の CSP とデザインは**全ページ共通で厳格**。ゲームごとに色・フォント・演出・スクリプトを変えるには、ページごとに CSP を緩め、CSS を足し、HP の build とテストを増やすことになる。HP の未コミット作業と同じリポジトリに、ゲーム 1 本ごとに手を入れることにもなる（承認も毎回必要）。**ゲームの大胆なアートディレクションと、HP のシックなデザインの維持は、別の場所に分けた方が両立しやすい。**

- **正本は WEB_GAMES の 1 か所**：ゲームを足しても、HP には手を入れない。
- **HP の GAMES**（別途承認）：当面は変更しない。後で、ポータルへの大きな導線と、注目 3 件程度を載せる（案は 5 章）。
- **URL**：`/<id>/` は開いた瞬間に遊べる（「URL を開くだけで遊べる」を守る）。`/<id>/about/` は詳細（遊び方・世界観・スクリーンショット・ランキング・製作メモ）。カードには「PLAY」と「詳細」の 2 つのボタン。
- 独自ドメインが取れたら、`games.<ドメイン>` に載せ替えられる（すべて相対パス。ドメインの購入は有料なので事前に相談）。

### フォルダ（`games/<id>/` を役割で分ける。`ball-dodge` を移す）
```
games/<id>/
├── game.json         共通の情報（id・題名・ジャンル・タグ・操作・スコア・機能・状態）
├── play/             ゲーム本体（index.html・main.js・assets/）→ /<id>/

│   └── about.html    （任意）完全に独自の詳細ページ
└── docs/             調査・仕様・バランス・テスト結果（公開しない）
```

## 3. Steam 型ポータルの実現方法
- **静的生成**（Python 標準機能。サーバー不要・無料）。`game.json` と `store.json` を集めて、トップ・ジャンル別・詳細・`games.json`（フィード）・`sitemap.xml` を作る。
- **トップ**：大きなヒーロー（注目のゲームのキービジュアル。CSS のスクロールスナップで切り替え、JS なしで動く）／新着／ジャンルの入口／全ゲームのカード一覧。カードは各ゲームの色（`theme.accent`）で色づけし、ゲームごとの個性が一覧からも見える。
- **絞り込み**：ジャンル・タグ・所要時間・操作（PC／スマホ）。小さな JS がフィード（`games.json`）を読んで絞り込み（JS が無効でも全件が見える）。ジャンル別ページは静的に作り、検索にも載る。
- **バッジ**：NEW・ランキングあり・スマホ対応など（`game.json` から自動）。人気順は、解析を入れない方針なので作らない（新着順・編集部のおすすめ順）。
- **画像の規格**（ゲームごとに用意）：ヒーロー 1280×720・カード 460×215・正方形アイコン 256・共有用 OGP 1200×630・スクリーンショット 3〜6 枚。
- **100 本以上**：カードは遅延読み込み。フィードは 1 ゲーム約 1KB なので 100 本でも 100KB 程度。ジャンル別の静的ページで分割。
- **iOS ゲーム**（STONE DASH など）も同じ一覧に載せられる（`platform: ios`・App Store へのリンク）。載せるかは決めてもらう。

## 4. ゲームごとに異なるデザインを実現する仕組み
**共通化は「情報の構造」と「最低限の機能」だけ。見た目は共通化しない。**

| 共通にする（固定） | ゲームごとに自由 |
|---|---|
| 情報の項目：題名・キャッチ・PLAY ボタン・ジャンル・操作・遊び方・スクリーンショット・ランキングの有無・プライバシー・一覧へ戻る | 色・フォント・背景・レイアウト・装飾・動き・効果音・キャラクター・文言のトーン |
| 小さな目立たない共通バー（「HENIQ GAMES ← 一覧」）と、フッター（プライバシー・お問い合わせ）。バーの色は CSS の変数で変えられる | `theme.css`（全面的に自由）／独自のフォント・画像・SVG／必要なら `about.html` を丸ごと独自に作る |
- 生成する HTML は**意味のある構造（見出し・セクション・図）だけで、見た目の既定を持たない骨組み**。見た目はすべて `theme.css` が決める。「既定のデザイン」を強制しない。
- **例**：BALL DODGE（カジュアル：明るくポップ）／CROWD SPRINT（レース：疾走感・斜めの構図・スピード線）／将来のホラー（暗く不気味）／物理演算カオス（派手でうるさい楽しさ）。
- **ガードレール（自動で検査）**：外部 URL なし／ページの容量予算／文字と背景のコントラスト（宣言された色の比で検査）／モバイルで横スクロールなし／`prefers-reduced-motion` を尊重（派手な動きの抑制）／点滅の上限（安全性）。スクリーンショット（幅 375・1280）を自動で撮り、見た目の確認に使う。
- **CSP**：ゲームのサイトは自由度の高い設定を使える（自サイトの JS・フォント・画像・音声）が、外部通信と外部素材は禁止のまま。例外が要るゲームは、そのゲームのパスだけに `_headers` で足す（HP と同じ仕組み）。

## 6. ゲーム完成から掲載までの自動化
1 コマンドの検査と生成（`python3 tools/build.py`）に、次を組み込む：
1. **検査**：`game.json`・`store.json` の項目、必要な画像（5 種）、文言の欠落、外部 URL、容量、コントラスト、アクセシビリティの基本。
2. **生成**：詳細ページ・カード・ジャンル別ページ・フィード・sitemap・OGP。
3. **テスト**：既存の自己テスト（3 画面幅）＋ゲーム固有のテスト＋紹介ページのスクリーンショット。
4. **公開前の関門（`status: published` にする条件）**：①ストアの素材がそろっている ②プライバシー情報（保存するデータ：`localStorage` の自己ベストなど／ランキングの Cookie）の記載 ③テストの成功 ④**あなたの公開の承認**。
5. **公開**：承認後に `git push` → Cloudflare Pages が自動デプロイ。公開後に `tools/verify_deployment.py`（HP の同名ツールを参考）で、トップ・詳細・ゲーム本体・ヘッダー・robots が正しいかを確認。
- 初期状態は `draft`（検索エンジンに載せない・robots は Disallow）。公開の承認まで変えない。
- **プライバシーの文面は、あなたの確認が必要**（私は法的な文面を断定しない。データの実態を一覧にまとめて提示する）。
