# BUTT SUMO オンライン対戦：技術調査と構成

## 1. 検討した構成
| 案 | 概要 | 評価 |
|---|---|---|
| **A. Cloudflare Workers + Durable Objects（採用）** | 試合ごとに 1 つの Durable Object（Room）が WebSocket を受け、サーバーが 30 Hz でシミュレーションを実行。マッチングと戦績は 1 つの Lobby（SQLite）。 | 既存の Cloudflare 環境・アカウントで足りる。サーバー権威にできる。無料プランで動く設計（SQLite 版の DO は無料プランで利用可）。 |
| B. P2P（WebRTC） | クライアント同士が直接通信。 | 勝敗をクライアントが決めるため不正対策不可。シグナリングにもサーバーが必要。**不採用**。 |
| C. D1 + ポーリング | HTTP の往復だけ。 | 30 Hz の対戦に向かない。**不採用**。 |
| D. 外部のゲームサーバー（Photon・Colyseus 等） | 有料／新規登録が必要。 | **不採用**（承認事項）。 |

## 2. 構成（実装済み・`server/butt-sumo/`）
- `core.js`：通信に依存しないロジック（**テスト済み**）。`RoomCore`（試合）・`LobbyCore`（マッチング・戦績・ランキング）・Elo。
- `worker.js`：Cloudflare 用の薄いラッパー（WebSocket・SQLite・タイマー）。`wrangler.toml` に Durable Objects の定義（`new_sqlite_classes`）。**実際の Cloudflare 上では未検証**（wrangler が無く、デプロイは承認事項のため）。
- `devhost.js` + `tools/dev_hub.py`：同じ `core.js` を、ブラウザのタブと本物の WebSocket で動かす開発用ホスト（実機テストで使用）。
- クライアント：`play/net.js`（通信）・`play/battle.js`（入力 30 Hz 送信・補間描画）。サーバーは `sim.js` の `step()` を実行し、スナップショット（約 450 バイト）を 30 Hz で送る。

## 3. 流れ
1. RANDOM MATCH → ロビーに WebSocket 接続（`hello`：端末 ID・ニックネーム）→ `welcome`（レート・戦績）。
2. `find`（キャラ選択）→ 待機。待ち時間が長いほど、組むレート差の許容が広がる（150 + 4 秒ごとに 60）。45 秒で見つからなければ「見つからなかった」。キャンセル可。
3. 成立 → 部屋 ID と、その試合だけのトークンが渡される → 部屋に接続（`join`）→ 両者が揃うと開始（15 秒来なければ無効試合）。
4. 試合中：クライアントは入力（スティック・ボタン）だけを送る。サーバーが物理と勝敗を決める。クライアントは約 90 ms 遅らせて補間描画。
5. 終了：サーバーが結果を Lobby に渡し、Elo でレートを更新（1 試合 1 回だけ・二重反映なし）。両者に結果と新しいレートを返す。

## 4. 不正対策・安全
- 勝敗・レート・戦績はサーバーだけが更新（クライアントの報告は使わない）。入力は丸める（スティック −1〜1、ボタン 4 ビット）。1 秒 100 通を超える入力は捨てる。突進・必殺は、サーバー側のスタミナ／クールダウン／ゲージで制限される（クライアントを改造しても連打できない）。
- メッセージ長 600 バイト上限・不正 JSON 破棄・hello 前は無反応・同じ端末 ID の 2 つ目の接続は古い方を切る・WebSocket の Origin 検査（本番は `https://heniq-games.pages.dev` のみ）。
- 勝ち星の譲り合い対策：同じ 2 人の 30 分以内 5 戦目から、レートが動かない。
- **残るリスク**：複数の端末 ID を使った自作自演（シビル攻撃）は防げない。ニックネームの不適切な語のフィルターは未実装（長さ・記号のみ）。キャラクターの解放状況はクライアント申告（全キャラの性能は公平に調整してあるため、不正に使えても有利にならない設計）。
- 切断：**再接続**（クライアントが 1.2 秒間隔で最大 6 回、同じ部屋に再参加。サーバーは 10 秒間、操作なしで試合を続けて待つ）。10 秒以内に戻らなければ**不戦敗**（相手の勝ち・レート反映）。両者が戻らなければ無効試合。

## 5. 費用・無料枠（Cloudflare Durable Objects／Workers、公式ドキュメントで確認：2026-11-23）
- 無料プラン：リクエスト 100,000 回／日、Duration 13,000 GB-s／日、SQLite の行の読み取り 500 万／日・書き込み 10 万／日。上限を超えると、その種類の操作が失敗する（課金はされない）。WebSocket のメッセージはリクエストとして数えられる（受信は 20:1 で換算と公式にある。**要最終確認**）。
- 概算（**実測ではなく設計上の見積もり**）：1 試合（最長 60 秒）の入力メッセージは、変化時と 0.1 秒ごとで最大 約 2,400 通 → 換算で約 120 リクエスト → 1 日 約 800 試合まで。1 試合の Room の Duration は 0.125 GB × 約 70 秒 ≒ 9 GB-s → 1 日 約 1,400 試合まで。
- **要注意**：Lobby は WebSocket が 1 つでも接続されている間、Duration が加算される（現在の実装は WebSocket Hibernation を使っていない）。1 日中誰かが接続していると、約 10,800 GB-s ≒ 無料枠の大半を使う。**公開前に Hibernation API（`ctx.acceptWebSocket`）へ移行する、または有料プラン（Workers Paid：月 $5〜）を検討する必要がある**（有料化は承認事項）。
- 同時接続数の上限：Lobby は 1 つの Durable Object なので、1 つのスレッドで処理できる範囲（数百接続程度が目安。**未計測**）。それ以上は、Lobby の分割が必要。
- 商用利用：Cloudflare の利用規約の範囲。広告・課金なしの無料ゲームのため、問題になる見込みは低い（法的な確認ではない）。

## 6. プライバシー・HENIQ ルールとの整合（要判断）
- サーバーに保存：端末 ID（ランダム）・ニックネーム・レート・勝敗・連勝。保存期間：試合のない端末は 30 日で削除。個人情報（氏名・メール・位置）は集めない。IP アドレスは Cloudflare が配信のために処理（HENIQ は保存しない）。
- **要判断（HENIQ のルール）**：「ブラウザに秘密の値（鍵・トークン）を保存しない」。端末 ID は、戦績を結びつけるための**持ち主を示す識別子**で、他人に知られると成りすませる性質がある（ランキングには出さない）。代案：①現状どおり（匿名・登録なし。ID の紛失＝戦績の消失）、②サーバーにアカウントを作る（登録・パスワード＝個人情報の取り扱いが増える）、③戦績をレート無しの「セッションだけ」にする。**私は①を実装した。公開前にオーナーの判断が必要**。
