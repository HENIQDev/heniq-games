# BUTT SUMO オンライン対戦：技術調査と構成

## 1. 検討した構成
| 案 | 概要 | 評価 |
|---|---|---|
| **A. Cloudflare Workers + Durable Objects（採用）** | 試合ごとに 1 つの Durable Object（Room）が WebSocket を受け、サーバーが 30 Hz でシミュレーションを実行。マッチングと戦績は 1 つの Lobby（SQLite）。 | 既存の Cloudflare 環境・アカウントで足りる。サーバー権威にできる。無料プランで動く設計（SQLite 版の DO は無料プランで利用可）。 |
| B. P2P（WebRTC） | クライアント同士が直接通信。 | 勝敗をクライアントが決めるため不正対策不可。シグナリングにもサーバーが必要。**不採用**。 |
| C. D1 + ポーリング | HTTP の往復だけ。 | 30 Hz の対戦に向かない。**不採用**。 |
| D. 外部のゲームサーバー（Photon・Colyseus 等） | 有料／新規登録が必要。 | **不採用**（承認事項）。 |

## 2. 構成（実装済み・`server/butt-sumo/`）
- `core.js`：通信に依存しないロジック（**テスト済み**）。`RoomCore`（試合）・`LobbyCore`（マッチング・戦績・ランキング・上限）・Elo。
- `worker.js`：Cloudflare 用の薄いラッパー。**省電力の作り**（3 を参照）。`wrangler.toml` に Durable Objects の定義（`new_sqlite_classes`）。**実際の Cloudflare 上では未検証**（wrangler が無く、デプロイは承認事項のため）。偽の Cloudflare 環境（`tests/js/worker_fake.mjs`）で、眠りからの復元・自動 ping・alarm・上限の流れを検査済み。
- `devhost.js` + `tools/dev_hub.py`：同じ `core.js` を、ブラウザのタブと本物の WebSocket で動かす開発用ホスト（実機テストで使用）。
- クライアント：`play/net.js`（通信）・`play/battle.js`（入力送信・補間描画）。サーバーは `sim.js` の `step()` を 30 Hz で実行し、スナップショットを送る。

## 3. 無料枠で安定して動かすための設計（2026-11-23）
**Cloudflare の公式ドキュメント（Durable Objects の料金・制限・WebSocket のページ。2026-11 更新分）で確認した事実**
| 事項 | 公式の記載 |
|---|---|
| 無料プランの 1 日の上限 | リクエスト 100,000／Duration 13,000 GB-s／SQLite の行の読み取り 5,000,000・書き込み 100,000／保存 5 GB。**超えると、その種類の操作が失敗する**（課金はされない）。UTC 0 時にリセット。SQLite 版の DO のみ使える |
| WebSocket のリクエスト換算 | 接続の確立に 1 リクエスト。**受信メッセージは 20:1**（100 通 = 5 リクエスト）。**送信メッセージと、プロトコルの ping は無料** |
| Duration と眠り | **標準の `accept()` は、接続されている間ずっと Duration が加算**される。**Hibernation API**（`ctx.acceptWebSocket`）なら、眠っている（メッセージのない）間は加算されない。`setInterval`・`setTimeout`・alarm は眠りを妨げる |
| 自動応答 | `setWebSocketAutoResponse` の応答は「追加の実行時間がかからず、課金されない」。リクエスト数に数えるかは明記なし（**要確認**） |
| alarm | 眠った DO を起こせる。1 回の呼び出しがリクエスト 1 回、`setAlarm()` が行の書き込み 1 回として数えられる |
| 1 つの DO の上限 | 1 秒 1,000 リクエストが目安（ソフトリミット）。同時 WebSocket 数は**数値の記載なし**。接続の添付データは 16,384 バイトまで |
| 注意（公式の記載が食い違う点） | 無料プランの保存容量は 5 GB／1 GB の両方の記載がある。無料プランの Worker の CPU 制限（10 ms／リクエスト）が DO に適用されるかは、ページ間で調整されていない（**要確認**） |

**これを受けた実装**
1. **Lobby は Hibernation API**：接続が開いたままでも、メッセージが無い間は眠る（Duration が加算されない）。接続と待機の状態は、接続ごとの添付データに保存し、起きたときに復元（`restoreConn`）。
2. **ping は自動応答**（`'ping'`→`'pong'`。眠ったまま返す）。クライアントはロビーに 5 秒ごと、試合中は部屋へ JSON の ping を 5 秒ごと。
3. **マッチングの定期処理は、待機中の人がいる間だけ**、5 秒ごとの alarm で動かす（誰も待っていなければ何も動かない）。新しい人が待機に入ったときは、その場で組み合わせを試す（待たせない）。
4. **Room は 30 Hz のタイマーが必要で、眠れない**。試合の間（最長約 70 秒＋終了後の 4〜8 秒）だけ動き、終わると止まって解放される。
5. **上限（超えたら「混み合っています」と断る。途中で無料枠が尽きて全員が落ちるのを防ぐ）**：同時接続 150／同時進行の試合 60／1 日の新規対戦 800／同じ接続元（IP の短いハッシュ）から 6 接続／ランキング問い合わせは 3 秒に 1 回／入力は 1 秒 100 通まで。
6. **書き込みの節約**：同じ ID・同じニックネームでの再接続は、保存しない。結果の保存は 1 試合 数行。
7. **クライアントの送信を抑える**：入力は変化したときだけ（最大 15 回／秒。突進・必殺は即時）、変化がなくても 0.25 秒ごとの生存通知。スティックは 0.1 刻み。

## 4. 流れ
1. RANDOM MATCH → ロビーに WebSocket 接続（`hello`：匿名 ID・ニックネーム）→ `welcome`（レート・戦績）。
2. `find`（キャラ選択）→ 待機。待ち時間が長いほど、組むレート差の許容が広がる（150 + 4 秒ごとに 60）。45 秒で見つからなければ「見つからなかった」。キャンセル可。
3. 成立 → 部屋 ID と、その試合だけのトークン（メモリ上だけ。ブラウザには保存しない）が渡される → 部屋に接続（`join`）→ 両者が揃うと開始（15 秒来なければ無効試合）。
4. 試合中：入力だけを送る。サーバーが物理と勝敗を決め、約 450 バイトのスナップショットを 30 Hz で送る。クライアントは約 90 ms 遅らせて補間描画。
5. 終了：サーバーが結果を Lobby に渡し、Elo でレートを更新（1 試合 1 回だけ）。両者に結果と新しいレートを返す。

## 5. 不正対策・安全
- 勝敗・レート・戦績はサーバーだけが更新（クライアントの報告は使わない）。入力は丸める。突進・必殺は、サーバー側のスタミナ／クールダウン／ゲージで制限される（クライアントを改造しても連打できない）。
- メッセージ長 600 バイト上限・不正 JSON 破棄・hello 前は無反応・WebSocket の Origin 検査（本番は `https://heniq-games.pages.dev` のみ）。
- 勝ち星の譲り合い対策：同じ 2 人の 30 分以内 5 戦目から、レートが動かない。
- **切断**：再接続（クライアントが 1.2 秒間隔で最大 6 回、同じ部屋へ。サーバーは 10 秒間、操作なしで待つ）。10 秒以内に戻らなければ**不戦敗**（相手の勝ち・レート反映）。両者が戻らなければ無効試合。
- **残るリスク**：複数の ID を使った自作自演（シビル攻撃）は防げない。ニックネームの不適切な語のフィルターは未実装（長さ・記号のみ）。キャラの解放状況はクライアント申告（全キャラの性能は同じ値なので、不正に使えても有利にならない）。

## 6. 匿名 ID（オーナーの決定：2026-11-23「アカウント登録不要の匿名方式」）
**方式**：ブラウザが作るランダムな 128 ビットの ID（`crypto.getRandomValues`）を、戦績の見出しとして使う。登録・メール・氏名・パスワードは求めない。
| 要件 | 実装 |
|---|---|
| ID を認証用の秘密として扱わない | 他のプレイヤーには**表示も送信もしない**（ランキング・対戦相手の情報に含まれるのはニックネーム・レート・キャラだけ）。サーバーのログにも出さない。ID を一覧・検索する機能は存在しない。**試合のトークンは試合ごとのランダム値で、メモリ上だけ**（ブラウザに保存しない） |
| ID を知っているだけでは、他人の戦績・アカウントを操作できない | **完全には保証できない**（認証の秘密を持たない設計の限界）。実装した防御：①ID は 128 ビットで推測できない／誰にも見えない②**待機中・対戦中の接続は、同じ ID の新しい接続に乗っ取られない**（拒否）③できることは「その匿名の戦績での対戦」と「その戦績の削除」に限られ、個人情報・ほかの戦績・ほかのゲームには届かない。ID が漏れる経路は、利用者の端末への不正アクセスや、ブラウザの保存データの持ち出し（XSS 等。CSP で外部スクリプトを禁止済み）に限られる |
| 戦績・レートはサーバー側で管理 | ブラウザに保存するのは ID だけ（戦績の数値はブラウザに保存しない。表示は毎回サーバーから） |
| プライバシー説明に記載 | `game.json` の `data`（詳細ページ・プライバシーページに反映）・設定画面の注意書き。保存する情報・期間・削除方法を明記 |
| 削除 | 設定の「オンライン戦績をサーバーから削除」（サーバーの記録を消し、ID を作り直す）。試合のない ID は 30 日、試合をした ID も 180 日来なければ自動削除 |
- **もっと強くしたい場合（実装していない・承認が必要）**：ID とは別に、ブラウザの「取り出せない暗号鍵」（WebCrypto の `extractable: false`）で署名して本人確認する方式。ID が漏れても成りすませないが、**ブラウザに認証用の鍵を保存することになる**ため、下の HENIQ ルールとの整合の判断が要る。

**HENIQ のルールとの再確認**（`WEB_GAMES/CLAUDE.md`：「ブラウザに秘密の値（鍵・トークン）を保存しない。保存してよいのは表示用の自己ベストだけ。ランキングは任意の別機能で、止まってもゲームは遊べること」）
- 匿名 ID は、上のとおり**認証用の秘密ではなく**、鍵・トークンにも当たらない → 「秘密の値を保存しない」には**抵触しない**。ランキングが止まってもゲームは遊べる（CP ステージは通信なし）→ この部分も満たす。
- ただし、後半の文「保存してよいのは表示用の自己ベストだけ」を文字どおりに読むと、**CP の進行状況・設定・匿名 ID の保存は、この文を超えている**（進行状況の保存は、今回の指示で必須とされたもの）。**提案：この一文を「保存してよいのは、表示用の自己ベスト・設定・進行状況・匿名の識別子（個人情報や認証の秘密でないもの）だけ」に改める**。CLAUDE.md の変更は、オーナーの承認後に行う（私は変更していない）。

## 7. 費用・無料枠の見積もり（**設計上の見積もり＋ローカルでの実測。Cloudflare 上での実測ではない**）
**実測した値（このMacのブラウザ。`tests/test_online.py` が `tests/_out/online_traffic.json` に出力）**
- 入力（受信）：キーを連打するボットで、1 人あたり約 4.4 通／秒（13 秒の試合で 59 通）。送信抑制の導入前の値。**導入後の上限は 15 通／秒**。
- 状態（送信）：約 30 通／秒・約 16 KB／秒／人（1 通 約 510 バイト。60 秒の試合で約 1 MB／人）。**送信は課金されない**が、利用者の通信量にはなる（スマホの回線では 1 試合 約 1 MB）。
- サーバーの CPU：1 ティック（シミュレーション＋スナップショット＋JSON 化）の平均 0.0045 ms、99 パーセンタイル 0.1 ms、最大 0.9 ms。

**1 日あたりの見積もり（上限 800 試合／日の場合）**
| 項目 | 計算 | 見積もり | 無料枠 |
|---|---|---|---|
| リクエスト（試合の入力） | 1 試合：2 人 ×（平均 5〜上限 15 通／秒）× 25〜60 秒 = 250〜1,800 通 → ÷20 | 約 13〜90／試合 | |
| リクエスト（接続など） | 接続の確立（ロビー・部屋）、hello／find／rank 等 | 約 6／試合 | |
| リクエスト（alarm） | 待機中だけ 5 秒ごと。最悪（誰かが常に待機）は 17,280／日 | 〜17,280／日 | |
| **リクエスト合計** | 800 × (19〜96) + alarm | **約 15,000〜95,000／日（最悪でも 100,000 未満）** | 100,000／日 |
| Duration（Room） | 部屋の稼働 約 35〜85 秒 × 0.125 GB = 4.4〜10.6 GB-s／試合 | 800 試合で 3,500〜8,500 GB-s | 13,000 GB-s／日 |
| Duration（Lobby） | 眠っている間は加算なし。メッセージ処理中だけ | 数十 GB-s 以下 | |
| SQLite の書き込み | 1 試合 約 6 行 ＋ 新規 ID ＋ alarm（`setAlarm` 1 回 = 1 行）≒ 4,800 + 3,000 + 17,280 | 約 25,000／日 | 100,000／日 |
| SQLite の読み取り | ランキング（3 秒に 1 回まで）・戦績の取得 | 数万〜数十万 | 5,000,000／日 |
- **無料枠の想定コスト：0 円**（上限 800 試合／日 の範囲。上限を超えたら新しい対戦を断るため、無料枠を超えて課金や全体の停止にはならない設計）。Workers の無料プランの Worker（ルーター）のリクエスト 100,000／日 も、接続の確立だけなので余裕がある（1 試合 約 4 リクエスト）。
- 有料化（Workers Paid：月 $5〜）が必要になるのは、**1 日 800 試合を超えて安定して遊ばれるとき**（公式の料金：リクエスト 100 万／月を超えた分 $0.15／100 万、Duration 40 万 GB-s／月を超えた分 $12.50／100 万 GB-s）。そのときは、承認を得て上限を上げる。
- **未検証**：①自動応答がリクエスト数に数えられるか（公式に明記なし。数えられても 1 接続あたり 12 回／分で小さい）②無料プランの CPU 制限（10 ms）が DO のタイマーに適用されるか（1 ティックは最大 0.9 ms なので、適用されても収まる見込み）③実際の同時接続数の上限（公式に数値なし）。**本番での確認が必要**。
